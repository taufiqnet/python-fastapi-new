Convert the employee Excel import into a resumable background job. On upload, save the file, create an ImportJob record (id, status, total_rows, processed, success_count, error_count, errors: list, cancelled: bool, business_id, created_by), return job_id immediately (202), and process rows in a background task (not blocking the request). Add GET /employees/import/{job_id}/status for polling and POST /employees/import/{job_id}/cancel to set the cancel flag, checked between row inserts so it stops promptly rather than instantly.

Add a floating, minimizable progress widget (not a modal) rendered globally in the base template, persisted via job_id in localStorage so it survives page navigation and reload — on any page load, check for an active job and resume polling if one exists. Show a progress bar, live counts, minimize/expand toggle, and a Cancel button. On completion, show a summary with a downloadable CSV of failed rows and their error reasons.

Keep existing employee creation/validation logic as-is — this task only changes execution from synchronous to background + adds the tracking/UI layer.

Before implementing: add require_permission("hrm", "employees", "create") and a business_id ownership check (job's business_id must match the acting user's) to all three new endpoints (status, errors-csv, cancel) — currently any authenticated user could access another business's import job by ID. Define the background processing function as sync (def, not async def) unless all its DB calls are genuinely async, so it doesn't block the event loop. Wrap each row's insert in its own try/except — log failures to errors and continue, never let one bad row abort the batch. Cap uploads at a reasonable row limit (e.g. 5,000) with a clear rejection message above that. If the server restarts mid-job, the job should be left in a distinguishable interrupted status on next startup, not stuck at processing indefinitely.
